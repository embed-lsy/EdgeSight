# EdgeSight

一个**跨平台单目视觉感知栈**：从摄像头画面中提取目标的**空间信息**（类别、距离、方位、碰撞风险），
为自动驾驶决策层提供输入。支持 Windows 与树莓派 Linux 双平台，本期在 Windows PC 上交付。
**不含执行器，不做车辆控制——它是一个纯粹的感知系统。**

> **⚠️ 升级进行中**：本项目正在进行「单目视觉感知栈」升级（相机真标定、几何测距等能力，见 `CHARTER.md`）。
> **当前开发重心在 Windows 端**；树莓派 Linux 端（`main_raspberry.py`）代码冻结、**正在升级开发中**，
> 升级完成后再同步移植，期间其行为以 main 分支历史版本为准。

## 为什么做 EdgeSight

我在东泉机器人实习，方向是**农业无人车底盘**研发，主要职责是**电机电控**，同时负责**选型**。

做测试时撞上一个绕不过去的问题：**超声波避障在农田杂草里误触发严重**——草叶就是“障碍物”，
车动不动就停。当时的备选有两条路：**UWB** 和**视觉**。UWB 测距是准的，但要在地里布基站，
**这套成本农业场景吃不下来**，所以最后定的是**低成本单目视觉**。回头看，这个选择是被需求
逼出来的——无人车真正需要的不是“有没有障碍物”，而是「**离障碍物还有几米**」，
而这正是单目图像 + 几何测距能回答的问题。

那次实习只走到方案评估，**没把「从一张图像拿到米制距离」这条链路真正打通**。实习结束后
我开始沿着这条线研究，就是要把这个既有项目升级成能输出**米制空间信息**的感知栈：
在**只有单目 USB 摄像头、没有激光雷达、没有独立显卡**的条件下，把
「检测 → 米制测距 → 碰撞风险预警」整条链路做出来，并**用卷尺实测误差**。

> 完整定位、成功判据与「明确不做」清单见 [`CHARTER.md`](CHARTER.md)。

## 功能特性

### 监视界面

- 实时显示原始图像与 AI 处理后的图像
- 叠加显示检测框坐标（x，y）、置信度、目标类别
- 支持实时微调置信度阈值与 NMS 阈值
- 实时展示推理 FPS 与画面 FPS
- **实时目标距离**：给出米制距离并标注用了哪种方法（接触点法 / 高度法 / 两法一致）；
  超出几何能力时**分两层降级**而不是丢掉信息：近场给带「？」的**宽度法参考值**，
  更近只给定性警报「进入减速/制动区」，**绝不给伪装成精确值的兜底数字**；
  不可测时把**原因**同时写进读数下面那行小字与悬停提示（脚被裁掉、框底边不在水平线以下、
  目标不完整……）
- **距离去噪**（`core/ranging_filter.py`，2026-09-26）：中值滤波（窗 3）
  + One Euro 自适应低通串联，专治检测框抖动与方法切换尖刺（实测
  0→4→0 m 会话：方向反转 42→12、切换区 P90 跳变 77→29 cm，对齐后
  残差 ~2 cm/帧、滞后 1 帧）。**位置紧跟测距，全链路只有一个距离值**：
  输出的规范值同时驱动速度门控、人特征档案、监视页读数、TTC、深度分析
  曲线与录制数据轨 —— 不存在"显示去噪、判定/存档用原始"的两套数。
  原始测量值只在录制轨留一份诊断字段 `distance_raw`（供事后重调滤波参数），
  实时逻辑一律不读
- **人员特征档案**（近场宽度法的精度来源）：目标完整入画并站定约 1 秒即自动量出
  **身高 / 肩宽**（存 `models/person_profile.json`），近场参考值改用「这个人自己的肩宽」；
  多人按躯干外观直方图区分
- **速度门控**：人不可能瞬移 —— 相邻读数的隐含速度超过人体极限（8 m/s）即拦下错值并说明，
  连续 3 帧一致或丢失 2 秒后自动重新锚定
- **TTC 碰撞预警（实时）**：距离读数下方的「碰撞预警」行实时显示碰撞时间与分级
  （提示 ≤4 s / 预警 ≤2.5 s / 危险 ≤1.2 s，分级着色）；近场参考级照例带「？」。
  速度估计带离群剔除与帧间守卫（IOU>0.3 + 类别一致），方法切换的振荡帧
  会被拒掉而不冒充 TTC；站定/远离不出数并说明原因（与录制回放的离线
  分析同一套估算器，语义完全一致）
- **安装参数自标定**：把目标摆到卷尺已知距离处各点一下，自动反解出
  「相机安装高度 + 俯仰角」并写回设置（详见上文「相机怎么装」）

### 深度分析界面

- **TTC 分析**：实时绘制碰撞时间曲线，三条分级阈值虚线（提示 4.0s /
  预警 2.5s / 危险 1.2s，与碰撞预警同源同参数），下方提示行给出当前
  TTC 告警状态与原因
- **目标距离分析**：实时距离曲线（中值 + One Euro 去噪后，与监视页读数
  同源），**曲线颜色区分目标类别**（人=绿、猫=橙……图例即类别名）；
  **没有读数的时段**（未检出 / 不可测）画成**红色 0 线**（图例「未知」）——
  距离被拉到 0 并标红，一眼看出「这段测不到」，而不是断线或消失
  （2026-09-26 定稿：整条时间线连续不断点，换段处共享边界点）。
  下方提示行显示当前测距方法。**图上不画方法竖虚线/标注**（2026-09-26）：
  pyqtgraph 把贴边文字的锚点当作数据点算进自动量程，配上"贴着视野顶摆"的
  定位就成了正反馈，会把 Y 轴一路推到几十米（实测复现：0.5~4 m 的曲线
  被压成一条直线、标签飘到 30 m 处重叠）—— 同样的信息改由提示行承载，
  不碰坐标轴
- 实时监控检测框置信度及其阈值变化趋势
- 绘制推理 FPS 波动曲线
- 可视化展示 CPU 与内存占用进度条

### 设置界面

- 灵活选择模型文件（支持 YOLOv5/v8 及其 INT8 量化模型）
  - Windows：仅支持 ONNX 格式
  - 树莓派 Linux：支持 ONNX 与 NCNN 格式
- 可选硬件加速器（CPU/GPU/NPU，依平台支持情况而定）
- 自定义目标选择规则（最高置信度/指定类别），在设置页选择后即时生效
- 相机标定：棋盘格采集 → 求解内参 → 持久化（`models/calib.json`），标定状态实时显示
- 相机设备记忆：内参**按设备指纹分档**存 `models/cameras.json`，换相机自动认出来、
  没标定会提醒标定、分辨率不符会拒用（像蓝牙配对一样记设备，见「多台相机 / 换相机」一节）
- 几何测距：**地面接触点法**（只需相机安装高度，不依赖目标身高，因此对未登记类别同样有效）
  与**高度法**（需已知目标真实高度）并行，两法不一致时标注「存疑」并同时给出两个数值；
  出数前先过可见性体检（框是否贴画面边界、**框顶边是否在相机水平线以上**、
  底边是否在相机水平线以下、反解身高是否荒谬）
- 近场降级（2026-09-25 晚间实证修订）：框底边进入画面底边 **12 px** 带内
  （脚贴近底缘或已出画——检测器在底缘有 5~16 px 系统性欠检，2 px 容差拦不住，
  曾把走回段读数整段冻结在 1.9 m）就不再信「框底边 = 脚」，依次给
  **宽度法参考值**（`Z = fx × 肩宽 / 框宽`，恒带「？」）与**定性警报**
  （「进入减速/制动区」，框宽占满画面 85% 或左右贴边时触发）；
  宽度法的前提是「框顶边必须在相机水平线以上」—— 只贴下沿的不完整框
  （上半身/一张脸）会被拒，因为它会给出方向危险的错值（实测把 2 m 的目标算成 4.54 m）
- **降级判定带滞回**（2026-09-26 治本修订）：底边进 12 px 即降级，但要**再往回收 12 px**
  才恢复精确读数。原因：底边帧间抖动实测中位 2.5~4.0 px、P90 11~17 px，
  无记忆的硬阈值会让方法在**阈值线上逐帧横跳**（四个「走回镜头」会话实测翻转
  26/28/34/20 次），读数在宽度法 1.4 m 与接触点法假值 1.95 m 之间交替，
  相邻帧斜率可达 3.9 m/s，把 TTC / 趋势估计整体毒化。加滞回后方法切换
  合计 66 → 14 次（−79%），帧间跳变 P90 38.5 → 17.8 cm。实测代价很小：
  58 帧被改判，其中 20 帧读数没实质变化（<5 cm）、33 帧是**纠正**（脚几何上
  不可能可见，接触点法读的是假底边）、仅 5 帧存疑且偏差 ≤14 cm 且方向偏近（安全侧）
- 安装参数：相机安装高度与俯仰角可手填，也可由「安装参数自标定」反解（见上文）
- 支持设置基准宽度、采样频率
- 一键应用运行参数并重载模型
- 可自由开启/关闭深度分析模块

### 录制回放界面

- **录制**：画面与检测/测距结果**分轨落盘**（视频轨 `video.avi` + 数据轨 `frames.jsonl`），
  写盘走独立线程与队列，不阻塞主链路；队列溢出导致的丢帧会**如实计数并提示**
- **录制时曲线实时绘制**：录制一开始曲线就从空开始长，每帧追加一个点
  （只记有读数的帧），并按当帧的 TTC 分级着色 —— 录完不必回放就能看出
  "哪一段进了提示/预警/危险"
- **回放**：视频轨与数据轨同步播放，支持进度条跳转定位；**播放速度按会话的
  真实帧率**（帧数 ÷ 真实时长），不是相机设置里的名义 fps —— 名义 30 fps 而
  本机实际只写出约 18.6 fps，按名义值播就是 1.6 倍快放
- **两轨对齐按时间，不按帧序号**：视频轨与数据轨**不是一比一**（实测一段
  20 s 的会话是 376 帧对 94 条记录），记录按「时刻 ≤ 该帧真实秒」匹配。
  曾用帧序号直接索引记录，导致后 75% 的播放时间拿不到数据（画面无框、
  无距离、曲线无从对齐）
- **回放分析**：测距曲线**随进度增长** —— 进度条走到哪，曲线就画到哪
  （拖动进度条即时揭示，可当缩略图用；按「停止」进度条与曲线一起归零），
  而不是加载时一次画满、播放时纹丝不动。曲线**按 TTC 分级分段着色** ——
  同一根线按分级换色（无告警=灰、提示=琥珀、预警=深橙、危险=红，图例带
  各级阈值），分级用的就是同一条规范距离序列，于是颜色直接回答"这段数据
  当时触发了哪一级告警"；**同一个分级出现的多个区间各自独立成段**，
  不会被连成一条横穿整幅图的直线（pyqtgraph 的画笔是每条曲线一个颜色，
  所以"一根线换色"拆成了多条同色曲线；段内换色处复用边界点保证不断线，
  段间用 NaN 隔断保证不横穿 —— 视觉上仍是**一条**曲线，只是颜色分了几段）。
  另有可测距帧占比、距离范围、平均置信度等摘要，
  并标注「录制时是否已标定」（未标定的距离值不可信）
- **数据轨的距离语义**：`distance` 存**规范值**（去噪后，与当时屏幕上的
  读数、当时的判定同源），`distance_raw` 另存原始测量值作诊断。旧格式录制
  （2026-09-26 之前，数据轨只有原始值）在回放/离线分析时**补做一次同参数
  去噪**，摘要里会注明 —— 保证"看到的曲线"与"算出来的结论"始终同源
- **TTC 碰撞预警**：对数据轨逐帧估算碰撞时间 `TTC = 距离 / 接近速率`
  （滑动窗口最小二乘 + 离群样本剔除）并分四级（无 / 提示 ≤4 s / 预警 ≤2.5 s /
  危险 ≤1.2 s）；目标关联守卫用「IOU>0.3 + 类别一致」，断连超时自动重置；
  近场（<约 2 m）的 TTC 如实标注「参考级」。离线 `analyze_recording()`
  跑录制回放可反复验证；监视页「目标位置」分组同款读数行**实时显示**
  （喂的是规范距离，即去噪后的值，与读数/曲线同源），分级着色、
  原因小字与距离行同款规则

> 为什么分轨存：把检测框烧进视频像素后，事后无法重新调参、无法重新测距。
> 分开存之后，**回放可以用新参数重新解算旧数据**，这才是"事后分析"的意义。

## 性能对比

> 分两部分：**本期实测**是 2026-09-22 在当前 Windows 机器上用固定脚本测出的数字，条件写明、可复现；
> **历史记录**来自早期树莓派 NCNN 阶段的开发日志，**未在本期硬件上复现**，保留作为研发历程。

### 本期实测（Windows PC，CPU 推理，2026-09-22）

**测试条件**：ThinkBook 14 G6 / i5-13420H（8 物理核 / 12 逻辑核）/ 16GB RAM /
Intel UHD 核显（**无独显**）/ ONNX Runtime 1.24.1 / **仅 CPUExecutionProvider** /
输入 1×3×640×640 / warmup 2 + 计时 5 次取均值。

| 模型                             | 精度   | 平均耗时            | FPS           | 备注                                   |
| ------------------------------ | ---- | --------------- | ------------- | ------------------------------------ |
| `yolov8n.onnx`                 | fp32 | 43–47 ms        | **21.3–23.1** | 默认线程数，检测主链路主力                        |
| `yolov8n.onnx`                 | int8 | 66.4 ms         | 15.1          | ⚠️ **比 fp32 还慢**，原因未做 profiling，不作断言 |
| `depth-anything-v2-small.onnx` | fp32 | 593 ms @518×518 | 1.69          | 稠密深度，按设计走异步旁路（8 线程）                  |
| `depth-anything-v2-small.onnx` | fp32 | 142 ms @224×224 | 7.04          | 降分辨率可提速，但深度精度会下降                     |

**线程数陷阱（实测）**：把 `intra_op_num_threads` 设为 **12**（＝逻辑核数）会让速度腰斩——
yolov8n 从 21.3 FPS 掉到 **10.4 FPS**，属线程超订；设 4 或 8 都在测量噪声范围内。
**本机物理核只有 8 个，不要按逻辑核数配线程。**

**两条结论**：

1. 检测单模型 21 FPS，相对「整链路 ≥15 FPS」门槛留出约 1.4× 余量
   （门槛 2026-09-26 由 ≥8 上调，对应定位 v1.3）；
2. 但**深度模型与检测串行只有约 1.0 FPS**（实测 1023 ms/帧）——这就是 CHARTER 规定
   稠密深度必须走**异步旁路**、且门槛只约束检测主链路的实测依据。

## 对标与边界

本项目刻意**对标开源社区同类项目**，而不是关起门来自己造。下表是每个对照物「拿了什么、
没拿什么、为什么」：

| 项目                    | 借鉴方式       | 具体落地                                                   | 不跟随的部分                                                            |
| --------------------- | ---------- | ------------------------------------------------------ | ----------------------------------------------------------------- |
| **Depth Anything V2** | ⚠️ **横评后不集成**（有证据地收档） | 用本机录制的真实视频、112 个几何可信点（1.9~6 m）离线横评米制版 | 结论：Hypersim 版中位误差 **57.9%**，且**误差随距离漂移**（尺度 0.60→0.83，对半交叉验证后仍 17%）——根因是官方 `infer_image` **不接受相机内参**，把训练集的焦距假设烧死在权重里 |
| **UniDepthV2** | ⚠️ **横评后不集成**（同上方法、同一批点） | 复用同一套横评流水线，按它要求的接口喂真实内参 K（含去畸变对照） | 结论：吃内参确实更好（去畸变后中位 25.2%），但**近场恰是最差段**（1.9~3 m 段 35.6%）；CPU **0.65 FPS**（1.55 s/帧），且许可为 CC BY-NC 4.0。近场改由几何分层方案覆盖，见「相机怎么装」一节 |
| **Supervision**       | ✅ 离线引入     | 用其 mAP / 混淆矩阵做**离线评测口径**，产出与社区可比的数字                    | **不进实时主链路**——本项目主链路有 ≥15 FPS 硬指标，不拿它冒险                             |
| **YOLOv8 / YOLO11**   | ✅ 主动横评     | 在同一段录制视频上对比 FPS 与检测质量                                  | 不做训练 / 微调（无独显，只用预训练权重推理）                                          |
| **YOLOPv2 / v3**      | ❌ 不采用      | 理由见下节                                                  | 多任务输出（检测 + 车道线 + 可行驶区域）不在本项目范围内                                   |
| **openpilot**         | 📖 对标不跟随   | 借鉴其**感知输出契约与分层**思想（感知层输出结构化空间信息）                       | 其规划 / 控制 / 世界模型不在范围内——本项目**不含执行器**                                |
| **Duckietown**        | 📖 对标不跟随   | 借鉴其**低成本可复现验证**方法论                                     | **不搭仿真**——本项目用「录制回放」兑现同一目的（不依赖现场路况即可反复演示）                         |

### 为什么不做多任务感知模型（YOLOP 类）

结论：**不采用**。两条硬理由，都可验证：

1. **算力过不了门槛。** 本项目门槛判据要求整条链路 ≥15 FPS。在本机（i5-13420H / Intel UHD 核显，
   仅 CPU 推理）实测现成的 `yolov8n.onnx`（约 8.7 GFLOPs）为 **19.49 FPS**，
   据此得到本机有效算力约 **170 GFLOPs/s**。YOLOPv3 约 30M 参数（≈9.4× yolov8n）且含两个分割头，
   **外推仅约 1–2 FPS**——距 15 FPS 门槛差一个数量级以上。
2. **场景与定位不匹配。** 车道线检测本就在「明确不做」清单里（防范围蔓延）；
   其训练数据（BDD100K 前视行车）与「单目米制空间感知」这条主线也不同源。

> 这不是「觉得没必要」，而是**实测外推后的取舍**——被问「为什么不加车道线」时，上面两条是答案。

### 部署标定：一共要做几次、换设备要重做什么

部署时要做的标定**只有两件**，各自**只做一次**、各自都能长期复用 —— 上层的
"棋盘标完还要再搞一次"不会发生，因为下面这两件事**互相独立、互不牵连**。

| 一次性的事 | 跟什么走 | 什么时候必须重做 | 落盘位置 |
| --- | --- | --- | --- |
| **相机内参**（fx / fy / cx / cy / 畸变） | **相机本体** | 换相机、换镜头、改分辨率 | `models/cameras.json`（**按设备分档**，见下节）+ `models/calib.json`（兼容旧版 / 树莓派端） |
| **安装参数**（相机高度 `H`、俯仰角 `θ`） | **机位** | 相机挪位置或重新固定 | `models/mount.json` |
| 目标真实高度表（人 1.70 m 等） | 无（常识先验） | **永远不用** | 代码内 `windows_global_params.py` |
| 本文档的摆位建议表 / 临界高度 | 内参 | 换相机后需重算（见下方提示） | 本文档 |

两条结论：

- **换相机 → 只重做内参（棋盘）**。`H`、`θ` 是**物理安装量**，与用哪台相机无关，
  可以直接沿用；目标高度表更不用动。深度测距模型是端到端的，也不受换相机影响。
- **挪机位 → 只重做安装参数**。内参不用碰。

两件都不需要量角器，安装参数**连卷尺量高度也不是必须的**：
「设置 → 相机标定」的棋盘标定只解决内参；`H` 与 `θ` 用「监视」页的
**安装参数自标定**同时解出来 —— 把目标摆到卷尺已知的 2 m / 5 m / 10 m 处
各点一次「记为采样点」，再点「求解安装参数」，它会一并给出两个值、
写回设置页并立即生效（还会给出不确定度）。相机装多高都能解，不必量角度。

两者都是**落盘一次、长期生效**：`models/` 下的 JSON 启动时自动加载，
重启程序不需要重填。这些文件都在 `.gitignore` 里（设备相关，不入库）。

### 多台相机 / 换相机：内参按设备记忆（像蓝牙配对那样）

一个 `calib.json` 装不下「多台相机」这件事：文件还是那个文件，程序照读不误 ——
**换一台同分辨率的相机会静默沿用旧内参**，距离系统性错，界面零提示
（相机驱动还会把画面调回 640×480，让尺寸"恰好"对得上，把问题盖得更严实）。

现在程序每次启动都会先认「本机是哪台相机」：枚举本机摄像头、算出**设备指纹**，
再按指纹到 `models/cameras.json` 里取对应内参。判定规则：

| 情况 | 程序怎么做 |
| --- | --- |
| 本设备有标定、分辨率相符 | 直接用，状态显示「已标定（本设备）」 |
| 本设备有标定、**分辨率不符**（换相机/改了分辨率） | **拒绝使用**并提示重标 —— 绝不用旧内参硬算 |
| 没有本设备档案，但有旧的 `calib.json` | 先照旧使用（老用户升级不受影响），状态标注「未绑定设备」，可一键**绑定到本设备** |
| 旧的 `calib.json` 盖着**另一台相机**的设备戳 | **拒绝使用**并提示重标 —— 这正是"换了一台同分辨率相机"的情形 |
| 什么都没有 | 不装内参（测距显示"不可测"），启动时弹一次「需要标定相机」提醒 |

**第一次插上一台新相机时**，你会看到一次「需要标定相机」的提醒，标定一次即可；
之后这台相机插回来直接可用，不再提醒。

**关于「设备戳」** —— 堵住最难发现的那个漏洞：给相机 A 标定完，之后插上一台
**同分辨率**的相机 B。这种情形下 B 的分辨率与旧标定"恰好对得上"，如果
`calib.json` 里连"这份标定属于谁"都没记，程序就只能含糊地"先沿用旧文件"，
于是 B 悄悄用上了 A 的内参 —— 距离系统性偏，而界面毫无提示。
所以新版本**标定成功（或手工绑定）后会顺手在 `calib.json` 里盖一个设备戳**，
之后插上别的相机时能明确说「这份标定属于另一台相机」并拒绝使用。
这个字段对旧版程序与树莓派端**完全无害**（读文件时会被忽略，`calib.json` 照常能用）。

**唯一需要你动手判断的情况**：本机有**多台**摄像头时（例如笔记本内置 + USB 外接），
Windows 上取不到「设备索引 ↔ 设备名」的对应关系（DirectShow 顺序不对外暴露，
OpenCV 也不提供设备名）。此时程序不会猜，而是列出检测到的设备，请你在
「设置 → 相机标定 → 本机摄像头」下拉框里**指明程序正在用的是哪一台**，之后会记住。

> **两个已知边界（如实说明，不是缺陷遗漏）**：
> ① 下拉框的语义是"确认身份"，**不是"切换相机"** —— 程序固定打开索引 0，
>    选它只是告诉程序"索引 0 是这台"，从而用对的内参；
> ② **同型号的两台**相机（硬件 VID/PID 完全相同）需要人工指认一次 ——
>    程序无法从硬件上区分它们，此时"设备戳"也帮不上忙（会被判成同一台）。
>    这是硬件层面无解，只能人工留意状态栏里显示的设备名。

> **换相机后要重算的还有一张表**：本文档下面「相机怎么装」一节的临界高度、
> 视野覆盖等数字都由内参（`fy` / `cy` / 画面高）算出，换相机或改分辨率后
> 必须重算。重算脚本：`E:\WorkBuddy-Work\scripts\plan_capture_mount.py`
> （读 `models/calib.json`，自动按新内参扫描摆位并打印速查表）。

## 相机怎么装：安装高度 × 俯仰角

几何测距（`Z = H_相机 / tan(俯仰角 + atan((v_底 − cy)/fy))`）里有两个必须知道的安装量：
**相机装多高 `H`**、**朝下多少度 `θ`**。这两个量互相牵制，装错了距离会成倍错 ——
下面把关系、误差怎么衰减、以及几组能直接照做的推荐数据讲清楚。

> 本节数字出自**本机实测标定**（`models/calib.json`：fx=772.8 / fy=783.7 / cx=305.7 /
> cy=283.9，画面 640×480，竖直视场 34°）。**换相机或改分辨率，这张表要重算** ——
> 公式都在下面，代入新的 `fy / cy / 画面高` 即可自己重算一遍。

### 一、两个量各自管什么

| 量        | 管什么                | 公式                                                |
| -------- | ------------------ | ------------------------------------------------- |
| 安装高度 `H` | **地面各距离落在多大的俯角上**  | `俯角 α(Z) = atan(H / Z)` —— 只由 H 和 Z 决定，**与俯仰角无关** |
| 俯仰角 `θ`  | **把这些俯角搬到画面的哪个高度** | `v(Z) = cy + fy·tan(α(Z) − θ)`                    |

换句话说：**H 决定"竖直视野怎么分配到地面上"，θ 只决定"把这片视野整体上下挪多少"。**
所以"H 和 θ 怎么搭配"其实是两件事：先把 H 定下来（视野分配），再用 θ 把它挪到画面正中。

装得越高，同一距离对应的俯角越大 —— 10 m 处：H=0.3 m 时 α=1.7°、H=1.0 m 时 α=5.7°、
H=2.0 m 时 α=11.3°。而 θ 挪过头就会把远处挤出画面（见第三节）。

### 二、误差怎么衰减（这是选装的依据）

三条独立误差来源，按方和根合成：

| 来源           | 公式                                                    | 特点                        |
| ------------ | ----------------------------------------------------- | ------------------------- |
| 俯仰角不准 `σθ`   | 精确 `2·σθ / sin 2α`（σθ 取弧度）；心算用 `≈ 1.745% × Z/H`（每 1°） | **与距离成正比、与安装高度成反比** ← 主导项 |
| 脚点像素定位 `σpx` | `2 / (sin2α·(1+u²)·fy) × σpx`                         | 大俯角（近处）时很小                |
| 安装高度不准 `σH`  | `σH / H`                                              | 与 H 成反比                   |

> **两个俯角式差多少**：`1.745% × Z/H` 除以精确式**恒等于 `cos²α`** ——
> 也就是说心算式**永远偏低**，偏低比例恰为 `sin²α`（α 是这个距离处的俯角，见下表）。
> 俯角小的时候几乎重合（α=5.7° 偏低 1.0%），俯角大时低估明显（α=16.7° 偏低 8.3%）。
> **本文所有表格里的数字都用精确式算**，心算式只用来快速估量级。

**10 m 处，每 1° 俯仰角误差带来的距离误差**（本机内参）：

| 安装高度 H         | 0.30 m    | 0.50 m | 0.70 m | 1.00 m | 1.35 m | 1.50 m | 2.00 m | 3.00 m   |
| -------------- | --------- | ------ | ------ | ------ | ------ | ------ | ------ | -------- |
| 10 m 处俯角 α     | 1.7°      | 2.9°   | 4.0°   | 5.7°   | 7.7°   | 8.5°   | 11.3°  | 16.7°    |
| 每 1° 的误差       | **58.2%** | 35.0%  | 25.1%  | 17.6%  | 13.2%  | 11.9%  | 9.1%   | **6.3%** |
| 自标定 σθ≈0.15° 下 | 8.7%      | 5.2%   | 3.8%   | 2.6%   | 2.0%   | 1.8%   | 1.4%   | 1.0%     |

两条反直觉但很要紧的结论：

1. **装得越高，远处越不怕角度误差**（因为有 `α = atan(H/Z)`，H 越大俯角越大，
   距离对角度误差就越不敏感）。代价是近处的脚点会被挤出画面（第三节）。
2. **「安装参数自标定」把 σθ 从量角器的 ±0.5° 压到约 ±0.15°。** 因为误差 ∝ 1/H，
   这**相当于免费把相机装高 3 倍** —— 这就是不推荐用卷尺+量角器硬量的原因。

固定 H=1.0 m 时，误差随距离增长：2 m **1.2%** ｜ 5 m **1.8%** ｜ 10 m **3.1%** ｜
20 m **5.9%** ｜ 50 m **14.6%**（其中俯角项分别是 0.7% / 1.4% / 2.6% / 5.2% / 13.1%）。

### 三、别把视野浪费掉：三个"能看到什么"的界限

除了"脚点必须在画面内""俯角必须 > 1°"，还有两条容易被忽略的界限：

| 界限                | 判据                             | 本机数值                                              |
| ----------------- | ------------------------------ | ------------------------------------------------- |
| 能同时看到 **2 m 的脚**  | 2 m 脚点要在画面下沿之上                 | H **≲ 1.9 m**（H > 1.91 m 时怎么调 θ 都进不来）             |
| 地平线要留在画面内         | `θ ≤ 光轴以上可见角`                  | H **≤ 1.35 m**（这里是不含边距的理想值；含 8 px 边距的严格值是 1.32 m） |
| 远处目标**上半身**要留在画面内 | `θ ≤ atan((H−1.7)/10) + 19.9°` | H **≤ 1.14 m**（含 1° 余量 1.08 m）—— 与上一条**同时**满足的临界  |

- 「地平线出画」的代价很实在：H=1.2 m 时，θ 只从 19.9° 再加大 6°，画面里的地面
  就从"一直延伸到地平线"缩到 **11 m 以内** —— 更远的地面整块看不见。
- 「远处目标上半身出画」的代价是 **高度法失效、两法互检永不触发**（`CHARTER` 第 4 条），
  只剩接触点法单打。所以对行人场景，**尽量别让 θ 大到把 10 m 处的头挤出画面**。

由「2 m 脚点入画」`atan(H/2) ≤ θ + 光轴以下可见角` 与「地平线在画面内」`θ ≤ 光轴以上可见角`
两条联立，可得一个与相机无关的判据：**`H ≤ 2·tan(竖直视场角)`**（本机 34° → 1.35 m）。

| 1.70  | 26.9 ~ 29.0° | **29.0°** | 0.8% | 1.1% | 1.8%  | 1.82 ~ 10.6 m | 只剩半身     |
| 1.80  | 28.5 ~ 29.6° | **29.6°** | 0.8% | 1.1% | 1.7%  | 1.89 ~ 10.6 m | 只剩半身     |
| 1.90  | 30.1 ~ 30.1° | **30.1°** | 0.8% | 1.0% | 1.6%  | 1.95 ~ 10.5 m | 只剩半身     |

**不想查表？两个式子就够了**（本机内参下的常数，换相机需重算）：

```
θ 可行区间：  atan(H/2) − 13.50°   ≤  θ  ≤  atan(H/10) + 19.39°
推荐 θ：      H ≤ 0.9 m          →  atan(H/2) − 10.5°
              0.9 < H ≤ 1.08 m   →  atan((H − 1.70)/10) + 18.4°
              H > 1.08 m         →  两全不可兼得，按表 2 取舍
```

（式子与表 2 有 ±0.1° 的取整差 —— 表 2 是逐 0.05° 扫描出来的，以它为准。）

**这组 H / θ 还决定了「最近能测多近」**（现场最常撞上的问题：目标一走近就显示「不可测」）：

```
Z_最近 = H / tan(θ + 画面下半视场角)        画面下半视场角 = atan((画面高 − cy) / fy)
```

含义：**画面最下面一行像素看向地面的距离**。比它更近的地面点根本不在画面里 ——
地面接触点法要求看得见脚，脚出画就没有**精确**读数（这是几何，不是模型或程序问题）。
脚出画之后程序**分两层降级**（2026-09-25 新增「宽度法」，纯软件、零硬件）：
① 约 0.6 m ~ 该距离之间给**参考值** `Z = fx × 肩宽 / 框宽`（读数带「？」、方法标「宽度法(参考)」，
肩宽优先用自动建立的人特征档案；人一侧身会高估，故恒为参考级）；
② 再近（框占满画面）只给**定性警报**「进入减速/制动区」，不编数字。
⚠️ **实际降级起点比几何值更早**：检测器在画面底缘欠检 5~16 px，框底边进入画面底边
12 px 带内（对应本机约 **2.0 m**）程序就不再信「框底边 = 脚」——否则接触点法会把
一切更近的距离读成几何下限（2026-09-25 实录：走回段读数整段冻结在 1.9 m）。
这个判定**带滞回**（2026-09-26）：进 12 px 降级，要**再往回收 12 px**（本机 456 px）
才恢复精确读数。所以站在 2 m 附近时读数**不会**在「精确值 / 参考值」之间逐帧跳 ——
代价是**退出略滞后**：在 456~468 这段缓冲带内沿用参考值（实测这些帧两法差值
中位 18.9 cm，且 57% 是「脚几何上不可能可见」的纠正，方向偏近即安全侧）。
滞回参数在 `core/calibration.py` 的 `FOOT_CLIP_TOL_PX` / `FOOT_CLIP_HYST_PX`，
选参依据见 `E:\WorkBuddy-Work\scripts\analyze_foot_state_flip.py`
与 `verify_foot_hysteresis_replay.py` / `verify_foot_hysteresis_cost.py`。
本机（640×480、fy≈783.7、cy≈283.9）下半视场角 ≈ **14.0°**，
例：H=0.65 m/θ=5° → 精确区最近 **1.88 m**，2 m 处脚点只剩 15 px 余量；按推荐式改到 θ=7.5° →
最近 **1.65 m**、余量 51 px。代价是近处的人**头顶出画**（只丢高度法与两法互检，接触点法仍可用）。
现场随时重算：`E:\WorkBuddy-Work\scripts\plan_near_field.py`（读 `models/` 下的标定与安装参数）。

两条规则（第一条现在有明确的上限数字了）：

1. **先看 H 是不是你能选的。**
   **选得了**（车顶/支架可调）→ 在 **1.08 m 以内尽量装高**（精度随 H 单调变好，
   且这个高度以内什么都丢不掉），本机就是表 1 的 **1.00 m**。
   **选不了**（车体结构定死）→ 查表 2，或代上面的式子。
2. **再定 θ**：取**刚好能让 2 m 脚点留在画面里**的那个最小俯仰角，再留 3° 余量。
   **不要为了"提高精度"把 θ 往大了调** —— 俯角项与 θ 无关，
   调大只会丢远场（实测：θ 从 13° 调到 25°，精度只提升约 0.1%）。

**三个临界高度**（车高落在这附近就要做取舍，表 2 里能看到对应的列怎么变）：

| 临界值            | 越过之后                                                                             |
| -------------- | -------------------------------------------------------------------------------- |
| H < **0.17 m** | 10 m 处俯角 < 1°，`Z = H/tan α` 发散，**接触点法本身失效**（与 θ 无关）。精确下限 = `10·tan 1°` = 0.175 m |
| H > **1.08 m** | 「2 m 脚点入画」与「10 m 处人头在画面内」**不可兼得**：想要远场互检，就得放弃 2 m 以内；想测近处，就得丢远场互检                |
| H > **1.32 m** | 地平线出画，画面里的地面缩到有限远处（表 2 的"地面"列从 `~ 地平线` 变成 `~ 17.4 m`）                            |
| H > **1.91 m** | 无解 —— 2 m 脚点怎么调 θ 都进不来                                                           |

> **「全身可见」只对 10 m 成立**：上表那一列说的是 **10 m 处**的目标。
> 俯仰角越大，越近的目标头顶越会被画面**上沿**裁掉 ——
> ① 摆平 3.45 m 以内、0.70 m 装 5.1 m 以内、**1.00 m 装 7.3 m 以内**，头顶就不在画面里了。
> 被裁掉头顶**不影响接触点法出数**（它只用框底边），但**近处的高度法/两法互检不成立**
> —— 互检只在远场可用。想让近处目标也全身入画，就把 θ 调小（代价是 10 m 处头顶贴边）。

**不想手算？直接让程序解**：在「监视」页用**安装参数自标定** ——
把目标摆到卷尺已知距离（推荐 **2 m / 5 m / 10 m** 三点）各点一次「记为采样点」，
再点「求解安装参数」，它会同时解出 **H 与 θ** 并写回设置页 ——
**这一步能替你验掉"实际装的高度/角度与想装的不一样"**（车体变形、支架歪斜都会偏）。
解出的不确定度（例如 `±0.6 cm / ±0.09°`）会一并给出。

> 为什么推荐三点而不是两点：两点标定的方程是**一元二次**，数学上存在两个同样吻合的解
> （典型是"低装+小平角"与"高装+大俯角"），程序会用物理高度范围剔除不合理那一支，
> 但**两点永远能严格拟合，因此查不出"把膝盖当成脚"这类标记错误**（残差恒为 0）；
> 三点就有冗余，能靠残差自查。

## 使用说明

1. **选择模型与标签**：在“设置”界面选择对应的模型文件（.onnx/.param）与标签文件（.txt）。
2. **配置硬件与规则**：选择硬件加速器、目标选择规则，设置基准宽度等参数。
3. **相机标定（首次使用前必做一次）**：打印一张 9×6 内角点棋盘格（**A4 100% 比例**，
   图在 [`docs/chessboard_A4_9x6_18mm.png`](docs/chessboard_A4_9x6_18mm.png)）。
   **「方格边长」必须以量出来的为准**：量图上那条 100 mm 的打印校验尺 ——
   正好 100 mm 就填 **18.0**，否则填 `18 × 实测量 ÷ 100`
   （本机打印机实测 **17.1**，程序默认值即为此值，换了打印机就要按校验尺重填）。
   在“设置 → 相机标定”中核对「方格边长」与实量一致后，
   点击“开始采集”，让棋盘格在画面中变换位置与倾斜角（覆盖四角、至少 10 帧），
   点击“求解并保存”（**不必先停止采集**；就算先点“停止采集”暂停，已采的帧也会保留）。
   内参会持久化，换相机才需重标。
   重投影误差 < 0.5 px 优秀、< 1.0 px 可接受；求解后若提示“质量存疑”，
   多半是棋盘姿态变化不够（只在同一角度平移），按提示重采即可。
4. **装相机并标定安装参数**：按上文「[相机怎么装](#相机怎么装安装高度--俯仰角)」把相机装好
   —— 高度**能自己选**就装 1.0 m 左右配 θ≈14°；高度**被车体定死**就拿实测值查那张 H→θ 表。
   然后在「监视」界面把目标摆到卷尺已知的 **2 m / 5 m / 10 m** 处，
   各点一次「记为采样点」，再点「求解安装参数」—— 程序会解出安装高度与俯仰角、写回设置页并立即生效。
   （也可以跳过这步：不填安装参数时仍能用高度法对完整可见的目标测距，
   但贴脸、被遮挡等部分可见的目标会一律显示「不可测」。）
5. **应用参数**：点击“应用参数”按钮使模型与运行参数生效（**此按钮不做相机标定**，
   相机内参由上面第 3 步的“求解并保存”负责）。
6. **实时监视**：在“监视”界面查看检测结果与**目标距离**读数，微调阈值以优化效果。
7. **深度分析**：在“深度分析”界面查看各指标曲线（含几何测距曲线），监控系统运行状态。
8. **录制回放**：在“录制回放”界面点击“开始录制”采集一段场景，
   停止后用“选择录制”载入该会话回放，查看测距曲线与统计摘要。
   回放不依赖现场路况，适合反复调参与演示。

> **验收测量协议见 [`EVALUATION.md`](EVALUATION.md)** —— 卷尺三点测距、整链路帧率、
> 录制回放三条判据各自「怎么量、记什么、合格线多少」都写在那里，含记录表模板。
> **要动手做实测，直接照 [`docs/操作指引.html`](docs/操作指引.html) 做** ——
> 同一套判据的「照着做」版：打印棋盘格 → 相机标定 → 三点测距 → 录制回放，
> 逐步操作、记录表、常见问题都在里面（这份和 EVALUATION.md 是配套的，必须同步改）。

## 研发历程

### 第 0 期 · 树莓派原型（2026-02 ~ 2026-03）

1. **初始阶段**：基于 ONNX Runtime 部署 YOLOv8 模型，在 PC 和树莓派上运行，发现树莓派性能不理想。
2. **量化尝试**：切换至 OpenCV DNN 并将模型量化为 INT8，PC 端速度提升约 4 倍，但树莓派无明显改善。
3. **模型对比**：尝试 YOLOv5 及其 INT8 模型，效果均不如 YOLOv8，决定继续基于 YOLOv8 优化。
4. **参数调优**：在树莓派上测试 YOLOv8 INT8，通过降低帧率、优化 ONNX 线程等方式摸清最佳参数，但性能提升有限。
5. **引擎切换**：转向 NCNN 引擎，在树莓派上测试 YOLOv8 NCNN 模型，解决虚假 FPS 问题后，真实 FPS 达 2.35（约 3 倍提升），但部署后出现检测框异常、置信度恒为 1 的问题。
6. **问题排查**：推测与 softmax 层有关，尝试后处理移除 softmax 未解决，最终切换至 YOLOv5 NCNN 方案，纯脚本测试 FPS 达 59.52，部署至主程序后 FPS 稳定在 1.8-2.0，检测框与置信度正常，CPU 占用极低。

> 第 0 期解决的是「**能不能跑起来**」——把 YOLO 在树莓派 4B 上压到能用的帧率。
> 但它的距离是 `基准宽度 / 检测框宽` 量出来的**相对比例**，相机从未标定过，
> 也没有任何误差实测。**第 1 期要补的正是这一块。**

### 第 1 期 · Windows 端感知栈升级（2026-09-22 ~ 09-25）

目标不是提速，而是让输出变成**可验收的米制空间信息**：「离几米」，以及「这个数字凭什么可信」。

1. **重新定位**：先写清「是什么、成功长什么样、什么明确不做」（`CHARTER.md` v1.0 → v1.2），再落地验收协议 [`EVALUATION.md`](EVALUATION.md)。
2. **相机真标定**取代伪标定：棋盘格 → `cv2.calibrateCamera` → 内参持久化；未标定或目标过小时**返回「不可测」，不猜数字**（合成棋盘反解 fx 误差 0.08%、重投影 0.11 px）。
3. **几何测距**取代伪测距：`Z = 基准宽度 / 检测框宽` 换成 `Z = fy × H_目标 / 检测框高`。
4. **录制回放（双轨落盘）**：画面存 `video.avi`、检测/测距结果存 `frames.jsonl`；
   刻意不把检测框烧进像素 —— 分开存，事后才能**用新参数重新解算旧数据**。
   踩的坑：测距原本只在「开绘图」时才计算，导致录制拿不到距离数据。
5. **现场可用性整改**（09-23）：①摄像头只看 `isOpened()`，「开了但读不到帧」也报成功（改为多后端重试 + 试读校验，打开 **6 s → 1.7 s**）；②点「求解」界面冻 **17~19 s**（标定计算同步跑在主线程 → 抽纯函数 + 子线程，求解槽返回 **0.000 s**）。并补齐监视页缺失的**距离读数**。
6. **测距可信性：门控 + 地面接触点法**（09-23 晚）：现场现象是「脸贴到摄像头前却显示 3 m」——复现后确认是高度法按「人 = 1.70 m」先验去除，把 **0.40 m 读成 2.96 m**。
   加入可见性体检 + **反解判据**（假设底边真贴地，这目标该有多高；`H_估计 < 0` 是零先验硬判据）
   + 两法互检，8 个场景的**说谎次数 3 → 0**。新增**地面接触点法**
     `Z = H_相机 / tan(俯仰角 + atan((v_底 − cy)/fy))`：不依赖目标身高，未登记类别同样出数。
   + 踩的坑：宽高比先验的判别力实测为 **0**（三个说谎场景全落在「站立的人」区间）；
     简化式 `H_目标 = H_相机 / k` 只在俯仰角 ≈ 0 时成立，俯仰角 4° 时把 5 m 处的完整人算成 2.65 m。
7. **安装参数自标定**（09-24）：把目标摆到卷尺已知距离处各点一下，同时反解**安装高度与俯仰角**，两个最容易量错的手工量一起消失；推荐 **2/5/10 m 三点**（两点标定的方程数学上必然严格吻合，查不出「把膝盖当成脚」这类标记错误）。
   
   踩的坑：早前得出「相机必须装 **0.7 m 以内**」，其实是扫描时自设了「脚点须在主点下方 15 px」的假余量 —— 真下限只由「10 m 处俯角 > 1°」决定，约 **0.17 m**；且高度超过 **1.08 m** 后「2 m 脚点入画」与「10 m 处人头留在画面内」不可兼得。
8. **部署标定「做一次就够」改造**（09-24）：以「别人拿到也能部署」为需求回查了一遍标定链路。
   ① `H`/`θ` 原先只活在内存里，自标定解完关掉程序就丢、下次开机要重解 —— 这才是
   "棋盘标完还得再搞一次"的真正来源，改为落盘 `models/mount.json`；
   ② 内参原先只有一个 `calib.json`，隐含假设「这台机器只有一台相机」，换一台**同分辨率**
   的相机会静默沿用旧内参（驱动还会把画面调回 640×480 把尺寸凑巧对齐，盖住问题）——
   改为按**设备指纹**分档存 `models/cameras.json`：启动先认设备、再取内参，
   分辨率不符就**拒用并提醒重标**（见「多台相机 / 换相机」一节）。
   踩的坑：回填控件跑在信号连接**之前**，出现「界面显示 1.20 m、内部状态仍是 0」的静默失效
   （界面看不出来，靠断言 `global_params` 才抓到）；判定被「相机打开后用真实分辨率复核」
   改写时只刷新了一个标签，出现「界面写已标定、实际已拒用」的自相矛盾，
   验证脚本靠「标签内容 == 判定结果」这条断言抓到。

9. **近场三层兜底（P1+）+ 回程读数冻结修复**（09-25 晚）：接触点法几何下限
   （约 1.85 m）以内从「不可测」降级为「参考值/警报」——宽度法参考值

   几何下限；新增 `FOOT_CLIP_TOL_PX=12`（覆盖实测欠检主区间），19:45 录制

10. **TTC 碰撞预警（离线优先）**（09-25 晚）：距离变化率 → 碰撞时间 → 分级。

    （真实窗口 + 真实检测回调）15/15：走近 6→1.6 m 分级从提示升到预警、

12. **「脚出画」判定加滞回 —— 方法逐帧横跳的治本**（09-26）：第 10 条记下的

    从源头解决。先量化：底边帧间抖动中位 2.5~4.0 px、P90 11~17 px，而判定是

13. **回放两轨按时间对齐 + 曲线随进度增长**（09-26）：用户反馈「点播放/停止，
    只有进度条在动」。查下去发现根因不在曲线，而在一处更基础的对齐缺陷：
    **视频轨与数据轨不是一比一** —— 三个会话实测都是「376 帧对 94 条记录」，
    而 `read()` 拿**帧序号**当记录下标用，于是只有前 25% 的播放时间有数据，
    后 75% 全部 `rec=None`（画面无框、无距离、曲线无从对齐）。同时发现
    VideoWriter 用名义 30 fps 写文件头、本机实际只写出约 18.6 fps，
    20.17 s 的真实会话按名义值只播 12.53 s（**1.61 倍快放**）。
    改法：以**真实秒**为唯一时间基 —— 帧序号经 `fps_actual`（帧数÷真实时长）
    换算成秒，记录用「t ≤ 该秒」匹配；`read()` 逐帧命中率 **25% → 99%**。
    曲线同时从「加载时一次画满、播放时纹丝不动」改成**增量追加、随进度揭示**
    （拖动进度条即时揭示、按停止与进度条一起归零），并且**录制时就实时画**
    （时间轴与数据轨同一个式子，录完自动挂回放时严丝合缝）。逐帧揭示的性能
    也是改过的：旧写法每帧 `removeItem` + 重建 N 个段对象，长会话下纯浪费，
    新写法每级一条曲线、换级复制边界点，追加是 O(1) 一笔。
    验证：对齐单元 25/25（含与独立实现逐帧对拍、退化与断档边界）、
    曲线同步端到端 28/28（揭示点数与独立口径逐帧一致 ×60 次取样、
    换色处 10 处换级全部不断线、录制期曲线随帧增长、`keep_curve` 保留整条）。
14. **回放曲线「一条线」修正：同色多段不得横穿**（09-26）：第 13 条改成
    「每级一条曲线 + 追加」后，用户随即发现「测距曲线理论上应该是一条曲线，
    只是线的颜色会有变化，但是现在有好多条线」。根因是**分条方式选错了**：
    pyqtgraph 的画笔是**每条曲线一个颜色**，所以「一根线换色」只能拆成多条，
    但把**同一分级的所有点**攒进同一个 item 时，pyqtgraph 会按数组顺序连折线
    —— 同一个分级出现的**多段不相邻区间**之间被拉出一条**横穿整幅图**的直线。
    他录的那个会话实测：灰色 4 段、预警 2 段、危险 2 段，修复前会有
    **5 处横穿**（灰 3 / 预警 1 / 危险 1），正是他看到的"好多条线"。
    改法：每段末尾补一个 **NaN** 收尾 + item 用 `connect='finite'` ——
    栅格化时 NaN 前后不再相连，同色多段各自独立。**只加 NaN 不够**：隔离探针
    （`probe_curve_break.py`）实测 `finite`+NaN → 路径断成 2 条独立子路径，
    `all`+NaN → 仍是一条。这样 item 数恒 ≤4（每级一条），图例天然是"每级
    一行"，不必手工维护；视觉上就是**一条**曲线，只是颜色分了几段。
    回归加了**双判据 + 反证**：① 结构层「每级独立子路径数 == 该级连续段数」；
    ② 语义层「同一条线上相邻两个真实点之间不得夹着别的分级」（**零阈值** ——
    首版用「间隔 > 3×帧间隔」的代理判据，被「数据轨采样率低于视频帧率、
    相邻曲线点天然隔 3~4 个帧间隔」坑出 82 处假报警）；③ 同一判据打在
    「修复前算法」上**必须报警**（否则该断言是永远通过的空转）。
    端到端 39/39，含在他实际录制的 `session-20260926-143517` 上复验
    （修复后横穿 0 处、逐级子路径数与段数一致）。
15. **检测后处理向量化 + person 白名单**（09-26，CHARTER v1.3 硬约束落地）：
    `postprocess_yolov8` 原是逐框 Python 循环 8400 个预测、每框
    `np.argmax(80)`，实测占整帧 43%（35 ms）。向量化重写后全程 numpy，
    **与旧版对拍逐字节一致**（`verify_postprocess_vec.py` 用 git HEAD 旧版
    做真参照：合成边界用例 + 真实会话 5 帧模型输出，字典列表全等），
    后处理单段中位 25.3 → 2.4 ms（空载实测，两遍换顺序复测；机器忙时
    绝对值变大但比值稳定 8~16×）。同时检测层接入 **person 白名单**
    （v1.3「全链路唯一类别」）：从标签文件归一化出 person 的 class_id
    （中英文标签都认），在 NMS **之前**过滤。语义是 **argmax 判定** ——
    「argmax=car 0.86 而 person=0.42」的框被丢弃，**不会**重标成
    person 0.42（那等于把车框伪造成行人，有专门用例钉死）。标签为空时
    白名单为 None（如实降级，不猜 COCO id 0）。验证 18/0，含端到端
    `predict`（真实会话 → 只出 person 目标）与两个语义边界用例。
    有两个判据是**测试写错、实现没错**才抓出来的：① NMSBoxes 的
    score_threshold 是**严格大于**（float32 下分数恰好==阈值 → 丢弃，
    旧实现同样如此，边界语义以实测为准）；② `Signal(dict)` 被
    `emit(None)` 触发时槽收到的是**空字典**而非 None（Shiboken 按默认值
    转换）—— 测试若按 `is None` 判无目标会误报。
