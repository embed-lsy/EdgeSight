## v1.5.0（2026-10-03，判据① 按场景收窄 —— **判据变更**）

判据① 实景测距由「误差 ≤15%（≤5 m）/ ≤20%（>5 m）」收窄为
**「误差 ≤15%（≤5 m）」**，`>5 m` 分支**移出本期验收项**。两条理由：

1. **本场景用不到** —— 本项目是农业车跟随，跟随目标与车辆的间距通常在 5 m 以内，
   `>5 m` 的测量分支在该场景下不会被触发；
2. **没有场地** —— 可用空间最大只能铺到约 5 m，铺不出 8~10 m 的实测点，
   该分支至今**没有验证过**。

⚠️ 因此「测距达标」这句话**必须带范围限定**：`≤5 m 内达标，最大相对误差 6.8%`。
不带限定的「测距精度 ±15%」是超出验证范围的说法。

**判据代码仍保留 `RANGING_LIMIT_FAR = 0.20`** —— 这是有意的：日后真补测了远场点
它能照常判，不会静默套用 15% 把远场误判成不合格。**保留判定能力 ≠ 该分支已达标**，
当前状态在闸门里单列为「不适用」，并在 `docs/验收实测.json` 的 `far_field` 写明理由
（不写理由会被退回「未覆盖」，而「未覆盖」在 `--strict` 下算不过）。

依据：2026-10-03 用户口头确认（「远场我真的没有场景测，农业车做跟随也不会离人这么远，
我们就实话实说」→「判据也要改，所有文档都要对齐，以代码为准」）。

配套：闸门新增判据⑥「判据数字与代码一致（以代码为准）」—— 起因是这次同步
CHARTER / EVALUATION / README 三处时，发现 README 里仍留着两处
「整链路 ≥15 FPS」，而该口径早在 v1.4.3 就已收窄为「推理 FPS」。

## v1.4.2（2026-10-02）

指纹与几何测距的**口径收正** —— 建档量出的**不是身高 / 肩宽**，而是
**检测框覆盖的真实尺寸（框跨度，纵 × 横）**，比真身高小约两成属预期
（本机先验 1.41 m）；几何测距 ① 由「身高法」改为**「框跨度法」**，
其 `H` 取框跨度而非身高。
依据：2026-10-02 实测建档值 1.4177 / 0.4707（与先验 1.41 差 0.5%）＋ 用户口头确认。
**只收正口径措辞，判据与范围不变。**
